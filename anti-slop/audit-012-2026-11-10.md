# Audit 012 — Accounts management moves to its own screen

Date: 2026-11-10
Branch: `arena/29099442-hissabook`
Reported: "Move accounts management to a separate page"

PR #25 shipped account management as a dialog raised from the overview's
overflow menu. This moves it to `/accounts` and deletes the dialog.

## Why a page and not a dialog

The dialog worked, but it was the wrong container for what the feature became.
Each account has three things a dialog could not show at once:

1. **Its balance**, which is derived and changes as the ledger changes.
2. **Its ledger context**, i.e. whether it has entries at all.
3. **The reason an action is refused.** An account with history can be renamed
   but not deleted; the opening balance freezes once entries exist.

In the dialog only (3) was visible, and only *after* the request came back 409.
A refusal the owner cannot see coming reads as a bug, not as a rule. A page has
room to state the rule before the tap, and room to show the balance beside the
name it belongs to. That is what drove the move, not aesthetics.

## What changed

**New route `app/accounts/`**, following the existing page pattern
(`app/transactions/page.tsx`, `app/inventory/page.tsx`):

- `page.tsx` — async server component. `requirePageMember([OWNER, ADMIN,
  BOOKKEEPER, VIEWER])` gates the screen; `getAccountsData(member.workspaceId)`
  runs on the server and its result is handed to the client as `initial`.
- `accounts-client.tsx` — the page itself: summary cards, add/edit form, account
  list.
- `loading.tsx` — the shared `AppLoading` shell, so a cold navigation paints the
  app's shape instead of a white screen.

**`lib/database.ts`** — one new export, `getAccountsData`, plus one new constant,
`ACCOUNT_BALANCE_SQL`. The balance expression is the important part: it used to
live inline inside `getDashboardData`, and copying it would have allowed the
overview and the page to drift apart as loan repayments are counted in one and
not the other. `getDashboardData` now interpolates the same constant, so the two
surfaces are structurally incapable of disagreeing. Verified against the running
server: dashboard `497,250` and page `497,250`, per-account identical.

**`app/api/accounts/route.ts`** — `GET` now returns the page payload
(`{accounts, total, workspace}`) with `balance`, `entryCount` and `hasHistory`
per account, instead of the bare create-picker shape.

**`components/accounts-dialog.tsx`** — deleted. Nothing else imported it.

**`app/dashboard.tsx`** — dialog and its open state removed. The panel keeps its
read-only summary (this was the deliberate scope call: only *management* moves).
Its overflow button is now a link to `/accounts`, and the panel footer gained a
"Manage accounts" link next to "Account activity". While here I fixed a label
bug: the panel tested for `MOBILE_WALLET`, but the API has always written
`MOBILE`, so a mobile wallet was described and drawn as a cash account.

**`components/app-sidebar.tsx`** — `Accounts` now points at `/accounts` instead
of scrolling back to `/#accounts`. On phones the fourth bottom-bar slot traded
`Stock` for `Accounts`: an owner reconciling a bank message reaches accounts far
more often than stock, and inventory is still two taps away in the sidebar menu.

## The rule the smoke test caught

First cut of `hasHistory` was `entryCount > 0 || openingBalance !== 0`. That
sounds safer, and it is wrong: the DELETE route refuses only on transaction
count, so a freshly created account with a PKR 25,000 opening balance was
reported as undeletable while the API would have deleted it happily.

Matching the API exactly matters more than being conservative, because the page
now uses `hasHistory` to decide whether to *render* a Remove button at all.
A wrong `hasHistory` no longer produces a 409 the owner can read; it produces a
missing button with no explanation. So:

- `hasHistory` is `entryCount > 0`, nothing else.
- Where removal is not offered the row shows a lock instead of a button, and the
  lock carries the reason in its accessible name and title.
- Two tests pin this down: one asserts the SQL condition matches the DELETE
  route's, the other that the page keeps a lock plus reason.

Confirmed against the server both ways: the account the page marked removable
deleted with 200; the two it marked locked returned 409 with the rename hint.

## Mobile

An account row on a phone carries an icon, a name, a balance and up to two
actions in roughly 360 px. Under `max-width: 640px` the action buttons grow from
32px to 36px, the row is allowed to wrap, and when it does the balance and
actions move to a second line together. The name keeps `min-width: 0` with a
120px flex basis so it never collapses to two letters.
