# Audit 011 — Bottom pill offset, white toaster, account management

Date: 2026-11-10
Branch: `arena/182e9dc7-hissabook`
Reported: "Inventory page, and teams page still shows incorrect mobile bottom
bar. Implement the accounts management. Fix the sileo toaster. Currently this
toaster has white background."

Three separate things. One of them turned out to be a different bug than the
report suggested, and I got part of it wrong before I got it right — both are
recorded below.

## 1. The bottom pill on Inventory and Team

### What was actually wrong

The report says the bar is "incorrect". I measured both screenshots (1080px
captures at ~2.62 DPR, so ~412 CSS px) rather than eyeballing them:

- Dashboard: pill spans x=173..965, left gap 173, right gap 115 — off-centre but
  symmetric-ish, and fully on screen.
- Inventory: the pill runs to the right edge with the "Menu" label clipped.

So the pill is not mis-styled. It is **pushed right because the page is wider
than the screen**. The cause is `.data-table { min-width: 720px }` inside a
~380px card on Inventory and Team. The wrapper could scroll, but nothing stopped
the table's intrinsic width from propagating up through the flex/grid parents,
so the layout viewport widened past the screen. A `position: fixed` element sizes
itself against the layout viewport, so the pill centred in the wider box and
rendered shifted relative to the glass.

### Fix

`.data-table-wrap` now carries `min-width: 0`, `max-width: 100%` and
`overscroll-behavior-x: contain` alongside its existing `overflow-x: auto`. That
contains a wide table inside its card instead of widening the document.
`card-header-row` and its children also get `min-width: 0`, and
`.inventory-search` gets `flex-shrink: 1`, because a fixed 260px search field in a
flex row is the same class of overflow.

### A change I made and then reverted

I first tried to make the pill immune by centring it with
`left: 50%; transform: translateX(-50%)`. The existing test suite rejected it:

> `centres the pill with insets, never a translate plus a scroll container`

That test encodes audit-006, where I made this exact change and it clipped the
pill off-centre on `/team`: a transform on a fixed element whose content becomes
a scroll container is clipped to a padding box centred on a point outside its own
box. I had reintroduced a bug I shipped and fixed weeks earlier.

Reverted to the proven form — `left: 10px; right: 10px; margin-inline: auto;
width: fit-content` — which cannot leave the viewport whatever its contents do,
and added `max-width: calc(100vw - 20px)` as a belt. The rule now carries a
comment naming the bad change so the next person does not reach for it either.
The tests caught this, which is the whole reason they exist.

## 2. The white toaster

The toast body was already dark. The white in the screenshot is the surfaces
**around** it: sileo draws the toast as an SVG pill plus a gooey canvas behind the
rounded corners, and those kept a pale default while `options.fill` only reached
the body layer.

### A wrong turn worth recording

I first "fixed" this by switching `theme="light"` to `theme="dark"`, reasoning
that the toast needed a dark palette. That was backwards. sileo's palette is
inverted on purpose because `theme` means "what colour is the page":

```
THEME_FILLS = { light: "#1a1a1a", dark: "#f2f2f2" }
```

`theme="light"` therefore means *dark toast on a light page*, which is exactly
right for us. My "fix" would have made the toast literally white. Reverted
before it shipped, and the reasoning is now in a comment in `app-toaster.tsx` so
nobody repeats it.

### Real fix

The CSS skin now pins every surface sileo paints:

- `[data-sileo-pill] { fill: #14231b !important }` — the body pill.
- `[data-sileo-canvas] svg, [data-sileo-svg] { background: transparent }` — the
  gooey canvas that filled the corners.
- `[data-sileo-description] { color: #b9cbb4 }` for both the base and the
  `data-theme=light` variant, since sileo keys that colour off the page theme and
  inverted our text.
- `[data-sileo-badge]` gets a light-on-dark treatment.

Verified in the **served** CSS, not just the source.

## 3. Account management

The accounts panel's `…` button raised a toast: "Account management is being
built." The panel behind it already listed every account and balance, so the only
missing piece was editing.

### What shipped

- `POST /api/accounts` — add an account (name, type, opening balance).
- `PATCH /api/accounts/[id]` — rename, retype, or set the opening balance.
- `DELETE /api/accounts/[id]` — remove an unused account.
- `GET /api/accounts` — the list, for pickers.
- `components/accounts-dialog.tsx` — the real UI, wired to the panel's `…`.
  Every response returns the recalculated dashboard payload, so the panel updates
  in place and the route cache is dropped.

### Rules, and why they are rules

- **The running balance is never typed.** It is derived from the ledger. A typed
  balance would invent money no transaction explains, which defeats the point of
  an attributable book.
- **The opening balance is editable only while the account has no
  transactions.** Before that it is a starting fact; after that it is history.
  Enforced server-side with a 409 and its own message.
- **An account with history can be renamed but not deleted**, so the ledger stays
  readable.
- **The last account cannot be deleted** — the book needs somewhere to post.
- **Owners and admins only.** Everyone else gets a 403; the dialog also hides the
  controls and says why.

Verified against a live server: create 201, rename 200, duplicate name 409,
opening-balance lock 409, delete-with-history 409, clean delete 200, and
unauthenticated calls 401.
