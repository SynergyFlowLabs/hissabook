## 1. The bottom bar on /team — cause found, not guessed

### What the screenshot actually shows

The bar is not clipped by its own styling. It is **displaced**, and its last item
is cut off by the screen edge. Measured from the capture (1080px wide at 2.625
DPR, so 411 CSS px):

- bar's left edge: x=478px → **182 CSS px**
- active "Team" item runs to the right edge and is cut

### The arithmetic that identifies the cause

The rule in force was `left:10px; right:10px; margin-inline:auto;
width:fit-content`. With that rule the bar is centred **inside its containing
block**, not inside the screen:

```
left = 10 + (containingBlock − 20 − barWidth) / 2
```

Solving for the block width that yields the measured 182px, with a bar of 372px:

```
10 + (736 − 20 − 372) / 2 = 182.0     measured: 182
```

736px = the `.data-table`'s `min-width: 720px` plus 16px of card padding. So the
page was laying out **736 CSS px wide on a 411px screen**, and the bar centred in
that instead of the viewport. That is why the bar drifted and the last item was
cut, and it is the same defect class as audit-006 — the earlier write-up blamed a
percentage-left plus centring transform, which was one way to trigger it, not the
cause.

### Why the previous fix did not hold

`.data-table-wrap` already had `min-width:0; max-width:100%; overflow-x:auto`.
That makes it a scroll container on paper, but the table's 720px intrinsic width
could still reach the initial containing block. `overflow-x: clip` on `html` and
`body` does not prevent that either: clip suppresses the scrollbar, it does not
stop a descendant from sizing the block.

The route-level skeleton was a second, independent source of the same widening:
`components/app-loading.tsx` rendered a bare `<table className="data-table">`
with no scroll wrapper at all. While a screen was loading, the page was 720px
wide — which is exactly when the owner's screen was captured.

### The fix

1. `.data-table-wrap` gains `contain: inline-size`. A child's inline size can no
   longer contribute to the container's own inline size, so the 720px table
   cannot widen the page at all. This is the actual fix; the surrounding
   `min-width`/`max-width` rules were necessary but not sufficient.
2. `components/app-loading.tsx` wraps its skeleton table in the same
   `.data-table-wrap` every real table uses. A skeleton must never lay out
   differently from the content it stands in for.
3. The bar's own rule no longer depends on the containing block for its
   placement. It is now `inset: auto 10px … 10px; width: auto` and centres its
   *contents*, so there is no shrink-to-fit width and no auto margin to resolve
   against anything but the box it is given. Items are `flex: 0 1 auto`, so the
   active pill hugs its label instead of stretching.
4. `.app-shell` is bounded by `max-width: 100vw` as a second line of defence.

Four tests pin this: the bar's rule contains `inset: auto 10px` and contains no
shrink-to-fit width or auto margins; the wrapper contains `contain: inline-size`;
no bare wide table exists anywhere, skeleton included.

## 2. Partners shares and profit sharing — already implemented

I found the feature fully built rather than absent: `lib/partners/store.ts`
(1034 lines), `lib/partners/ledger.ts` (330 lines with 28 passing tests), ten API
routes, and a 1272-line partner screen. Rather than rebuild it, I verified it
against the running server.

### What exists

- **Shares**: `owners.share` plus an effective-dated `owner_share_changes` table.
  A share change never edits the old number; it appends a dated row.
- **Day-weighted profit split**: `dayWeightedPsr` weights each partner's share by
  the days it was in force across the period, so a mid-period change is honoured
  for the part of the period it applied to.
- **The s.13 appropriation waterfall**: deed-fixed partner salary, then interest
  on capital only out of what remains, then interest on drawings added back, then
  the residual split by the day-weighted ratio.
- **Posting and reversal**: a distribution posts `PROFIT_SHARE` / `LOSS_SHARE`
  entries into each partner's running hisaab; the database enforces one POSTED
  distribution per period; a void appends mirrored `CORRECTION` entries instead
  of deleting history.

### Verified live, then reverted

- October preview: basis profit PKR 46,000 over 31 days, residual 46,000.
- Posted a real November distribution: `201`, `residual: -18500`, and each partner
  received a `LOSS_SHARE` debit of 8,325 / 6,475 / 3,700 — exactly 45 / 35 / 20
  percent of the loss.
- Voided it: `200`, the entries reversed, and every partner balance returned to
  where it started. Demo workspace left as found (one POSTED distribution for
  October, partners net 20,700 / 24,600 / −15,800).

Five tests now pin the wiring: the page exposes both controls, every write route
is gated to owner/admin, shares recompute from dated rows, the per-period unique
index exists, and a void reverses rather than deletes.

## What I did not do

I did not add a server-rendered payload to `/partners`. It still fetches on the
client and shows the skeleton first, which costs one skeleton beat on a cold
load — worth doing, but it is a performance change to a working feature, not the
feature that was asked for, and folding it into this PR would have muddied a
focused fix.
