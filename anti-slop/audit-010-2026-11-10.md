# Audit 010 — Skeleton loaders everywhere

Date: 2026-11-10
Branch: `arena/c36e1493-hissabook`
Request: "In /transactions add the loader when data is loaded in All activity.
Also add loaders everywhere. Skeleton loaders."

## The specific bug in All activity

The table rendered exactly one placeholder cell while loading:

```tsx
{loading && !data ? <tr><td colSpan={8} className="ledger-message">Loading activity…</td></tr> : …}
```

One row of muted text under eight column headings reads as an empty table, not
as work in progress — and because it was one row in a table that later filled
with eight, the page grew by seven rows the moment data landed.

Now the table draws eight skeleton rows with the same cell rhythm as real data,
so the header stays put and nothing reflows when the rows arrive.

A second, quieter problem: changing a filter or turning a page while rows were
already on screen did nothing visible. `loading` was true, but the old rows just
sat there until the response replaced them, so a tap felt ignored. The wrapper
now carries `is-refreshing` (drops to 55% opacity) and `aria-busy`, so the tap
has an immediate, honest effect.

## Loaders everywhere

Before this, loading UI was inconsistent: a full-screen "Opening your business
books…" on Overview, a bare sentence on Team and Inventory, an "empty-state" box
on Partners, a spinner line on Reports, and a text cell in the ledger. Five
different idioms for one concept.

Every screen now uses one set of primitives (`components/skeletons.tsx`) and one
shimmer (`app/globals.css`, "Skeleton loaders"), matching the shimmer the
notification panel already had so the product breathes at one rhythm.

| screen | before | now |
|---|---|---|
| Overview | full-screen logo + "Opening your business books…" | real topbar and heading, hero card and content blocks drawn in place |
| Transactions | one "Loading activity…" cell | 8 skeleton rows, dimmed stale rows on filter change |
| Team | full-screen "Loading team records…" | real chrome, KPI cards, directory rows, members table |
| Inventory | full-screen "Loading inventory…" | real chrome, KPI cards, stock table, two cards |
| Partners | "Loading partner records…" box | real chrome, KPI cards, partners table, distribution list |
| Reports | spinner + "Building the report…" | KPI cards, chart block, table lines |
| any route, first navigation | white screen | `loading.tsx` per route → `AppLoading` |

### Why the skeletons keep the real topbar

Each skeleton renders the screen's actual breadcrumb, heading and subtitle. The
point of a skeleton is that the layout does not move; replacing the whole page
with a centred spinner throws away the frame and then rebuilds it, which reads as
two separate page loads.

### Scoping the route fallback

`loading.tsx` is added per authenticated route (`/transactions`, `/team`,
`/inventory`, `/partners`, `/reports`), **not** at the app root. A root
`app/loading.tsx` would have drawn a dashboard-shaped skeleton over the marketing
landing page and the sign-in forms, which have nothing to do with it. This is the
same class of mistake as audit 009's shell-on-the-landing-page bug, so it is
guarded by a test that asserts no root `loading.tsx` exists.

## Details worth recording

- **Dark surfaces.** The hero balance card needs light bars, not dark ones, so
  `.sk-on-dark` swaps the tint. Eight bars in the dashboard hero use it.
- **Reduced motion.** A sliding gradient is decorative movement. Under
  `prefers-reduced-motion` the animation stops and the bar holds a flat tint, so
  the shape still communicates "something is coming" without motion. Verified in
  the *served* CSS (`.sk{background:var(--sk-tint-strong);animation:none}`), not
  just the source.
- **Announcements.** Each skeleton region carries one visually-hidden
  `role="status"` ("Loading team records") instead of making twenty decorative
  bars individually readable.
- **Errors are not skeletons.** A failed load keeps the explicit error screen
  with a retry, because waiting will not fix it. Only genuine in-flight states
  became skeletons.

  six screens; All activity uses skeleton rows and no "Loading activity…"; a
  `loading.tsx` exists per authenticated route; no root `loading.tsx`; shimmer

- Fresh database, signed in: skeleton markup present in the SSR HTML on all six

  Reports 33). Zero occurrences of the old "Opening your business books".
- Confirmed the route fallback is genuinely wired, not just present as a file:
  the RSC payload for `/team` contains `"loading":[[… "className":"app-shell" …]]`,
  and the streamed HTML for `/transactions` shows React's suspense markers
  (`<!--$?-->`, `<template id="B:0">`, two `$RC` replacements) — the fallback is
  flushed first and swapped for the real screen, which is the intended behaviour
  rather than duplicate markup.
- Row counts check out arithmetically: 8 ledger skeleton rows + 6 fallback rows
  = the 14 `sk-row` occurrences in the response.

## Honest limit

There is no browser here, so I verified the skeleton *markup and CSS* and the
streaming mechanics, not what the shimmer looks like in motion on a phone. The
shimmer reuses the notification panel's existing gradient and 1.4s timing, which
has already shipped and been seen, so the risk is low — but the owner's own look
is still the acceptance check.
