# Audit 009 — Shell leaking onto the landing page, dead landing CTAs

Date: 2026-11-10
Branch: `arena/eb2f46e5-hissabook`
Reported: "Mobile navigation bottom bar is also showing on the landing page
please remove this. And button clicks are not working for example the try demo
and the other buttons are not working."

Two separate reports. One is a regression I introduced in tranche E. The other
is not, and I have been careful below not to claim more than I can show.

## Bug 1 — the shell on the landing page (my regression, confirmed)

Tranche E moved `AppSidebar` into `app/layout.tsx` and hid it with a list of
paths:

```
const SHELL_HIDDEN = ['/login', '/setup', '/invite'];
```

That list is wrong for `/`. `app/page.tsx` renders `LandingPage` for a visitor
with no session and `Dashboard` for a signed-in owner — the same URL, two
completely different pages. Gating on the path alone drew the sidebar, the
bottom pill and the mobile menu over the marketing hero.

Reproduced exactly, unauthenticated, before the fix:

```
landing-page present: 1
aside.sidebar:        1
mobile-nav:           3      <- the pill and its items
```

The screenshot confirms it: the pill sits inside the "SAFA STUDIO · SAMPLE"
preview card in the screenshot, which is the live shell drawn over the page's
own illustrative mock-up of the same pill. That is why it looked doubled.

### Fix

`components/shell-gate.tsx`: a server component that asks the real question —
is there a session? — instead of inferring it from the URL.

```tsx
export default async function ShellGate({ signedIn }: { signedIn?: boolean }) {
  if (signedIn === false) return null;
  return <AppShell />;
}
```

`app/layout.tsx` is now `async` and resolves `currentSession()` once per
document request, then hands the answer down. Consequences that matter:

- The decision is made on the server, so there is no flash of the wrong shell
  and no extra request on the client.
- It covers every future public route without anyone remembering to extend a
  list.
- `SHELL_HIDDEN` stays as a second guard, so a session that exists but is on an
  auth page still renders no shell.

Verified after the fix:

| request | aside | pill |
|---|---:|---:|
| `/` (no session) | 0 | 0 |
| `/login` | 0 | 0 |
| `/setup` | 0 | 0 |
| `/invite/x` | 0 | 0 |
| `/` (signed in) | 1 | 1 |
| `/transactions`, `/inventory`, `/team`, `/partners`, `/reports` (signed in) | 1 each | 1 each |

## Bug 2 — dead landing CTAs

I could not reproduce this and I am not going to pretend otherwise.

What I can show:

- The seven landing CTAs were `next/link`, i.e. they depended on the client
  router booting. If hydration fails or is delayed — a slow phone, a blocked
  chunk, an error in any client component in the tree — the markup still paints
  and the buttons still look right, but the tap does nothing. That is exactly
  the symptom described, and it is a real fragility regardless of the trigger.
- The shell was in the client tree on that page (bug 1). Every component it
  mounts — the notification poll, the mobile menu, the portal, the store — was
  being started over a static marketing page for a visitor with no account.
  Removing it (bug 1) removes that whole failure surface from `/`.

### Fix

The landing page's CTAs are now plain anchors. A marketing page's only jobs are
"read this" and "go to /login or /setup", so it should not require JavaScript to
perform its primary action. If the bundle fails for any reason, an anchor still
navigates. The signed-in app keeps `next/link`, where the client transition is
the point.

### What I could not do, and what I tried

The sandbox has no browser. I tried jsdom and then a hand-built `node:vm` DOM to
execute the real chunks and catch a hydration exception. Both failed for
environmental reasons (jsdom cannot parse Turbopack chunks; the vm stub does not
satisfy the Next client runtime) and produced no trustworthy signal, so I
discarded that line rather than report a guess as a finding.

One clue I could not explain and am deliberately not inventing an explanation
for: the screenshot's URL bar reads `hissabook-eta.vercel.app/#c…`. The landing
page contains no hash links and no element `id`s, so I cannot account for that
fragment from the app's own markup. It may be Chrome's find-in-page or a
recording artefact. If taps are still dead after this ships, that fragment is
the next thing to look at, and the browser console would name the cause in one
line.

## Guards added

- The shell is gated on the session, not a path list; the landing page renders no
  shell and mounts no `AppSidebar`.
- No `next/link` and no `<Link` in the landing page; `/login` and `/setup` are
  reachable as plain anchors.
- The existing "shell mounted once from the layout" guard now points at
  `ShellGate`, which is what caught the change when I made it.

**96/96** tests, `tsc` clean, build green, fresh-database smoke across all six
screens plus the four public routes.
